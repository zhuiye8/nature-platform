# 质量审核流程（业务对接用）

## 整体流程图

```
现场测评
   │ PM 上传测评成果 + 点"发起质量审核"
   ▼
整体技术审核（1 人）
   │ 通过
   ▼
内容审核（3 人并行：技术 + 管理 + 网络）
   │ 全部通过
   ▼
报告分配（分配人选定编制人）
   │ 通过
   ▼
报告编制（编制人上传报告）
   │ 通过
   ▼
最终审核（部门经理）
   │ 通过
   ▼
材料归档
```

---

## 节点详情

### 1. 现场测评

| 项 | 说明 |
|---|---|
| 谁在做 | 项目经理 PM + 测评师们（项目登记审批时分配的成员）|
| 做什么 | 各自上传自己负责的资料；PM 整理出"测评成果"文件 |
| 怎么结束 | PM 点"发起质量审核"按钮 |
| 必填项 | **测评成果池至少有 1 个文件**，否则不能发起质量审核 |
| 下一步 | → 整体技术审核 |

---

### 2. 整体技术审核

| 项 | 说明 |
|---|---|
| 谁在做 | 整体技术审核员（角色：tech_reviewer），系统从角色池里挑非本项目成员 |
| 任务分配方式 | **抢单制**：所有技术审核员都能看到这条任务，**先点先得** |
| 回避规则 | 当前项目的 PM 和测评师**不能**审核自己项目（除非池里全是自己人，兜底放行）|
| 操作选项 | **通过** / **复核** / **驳回**（系统另预留**调整**动作但暂未启用，详见后文）|
| 通过后 | → 内容审核（3 路并行同时开始）|
| 复核后 | 当前节点不动，PM 收到整改通知，整改完后原审核员重新审 |
| 驳回后 | → 回现场测评，PM 重做整套测评 |

---

### 3. 内容审核（3 路并行）

| 项 | 说明 |
|---|---|
| 谁在做 | 3 个人**同时**审核：<br>• 内容审核员-技术（content_reviewer_tech）<br>• 内容审核员-管理（content_reviewer_mgmt）<br>• 内容审核员-网络（content_reviewer_network） |
| 任务分配方式 | **定向分配**：进入节点时一次性分给 3 个具体的人，不是抢单 |
| 回避规则 | 同上，回避当前项目成员 |
| 操作选项 | 每人独立操作：**通过** / **复核** / **驳回**（系统另预留**调整**动作但暂未启用）|
| 全部通过 | → 报告分配 |
| 任一人复核 | ⚠️ **三人的任务全部进入"待整改"**（已通过的人也要重新审），PM 整改后所有人重新审 |
| 任一人驳回 | → 回现场测评，PM 重做 |

> **业务方需要讨论**：内容审核任一人"复核"会让已经通过的另外两人也要重新审核。这是当前系统行为。如果业务上认为"已通过的不该重审"，需要改设计。

---

### 4. 报告分配

| 项 | 说明 |
|---|---|
| 谁在做 | 报告分配人（report_assigner）|
| 任务分配方式 | 抢单制 |
| 做什么 | **必须选定一位报告编制人**（report_writer），然后填意见 + 点通过 |
| 操作选项 | **通过** / **复核** / **驳回**（系统另预留**调整**动作但暂未启用）|
| 通过后 | 系统自动把编制人写入项目成员，并把下一步"报告编制"任务定向分配给他 → 进入报告编制 |
| 复核后 | 当前节点不动，PM 收到整改通知 |
| 驳回后 | → 回现场测评 |

---

### 5. 报告编制

| 项 | 说明 |
|---|---|
| 谁在做 | 报告分配阶段选定的那位报告编制人 |
| 任务分配方式 | 定向分配（其他编制员看不到这条任务）|
| 做什么 | **必须上传至少 1 个编制报告文件**，否则不能点通过 |
| 操作选项 | **通过** / **复核** / **驳回**（系统另预留**调整**动作但暂未启用）|
| 通过后 | → 最终审核 |
| 复核后 | 当前节点不动，PM 收到整改通知 |
| 驳回后 | → 回现场测评 |

---

### 6. 最终审核 ⭐

| 项 | 说明 |
|---|---|
| 谁在做 | 部门经理（dept_manager）|
| 任务分配方式 | 抢单制 |
| 操作选项 | **通过** / **复核** / **驳回**（系统另预留**调整**动作但暂未启用）|
| 通过后 | → 材料归档（离开质量审核闭环）|
| **复核后** | → **回到报告编制**，原编制人继续改报告 |
| **驳回后** | → **回到现场测评**，PM 重做整套测评 + 4 路质量审核 + 报告 |

---

## 驳回路径速查表

### 当前已启用的动作

| 触发节点 | 触发动作 | 实际回到哪 | 影响范围 |
|---|---|---|---|
| 整体技术审核 | 驳回 | 现场测评 | PM 整套重做（包括 4 路质量审核 + 报告）|
| 整体技术审核 | 复核 | 原节点不动 | PM 整改测评成果，原审核员重审 |
| 内容审核（任一路）| 驳回 | 现场测评 | PM 整套重做 |
| 内容审核（任一路）| 复核 | 原节点不动 | PM 整改，**3 个审核人全部重审** |
| 报告分配 | 驳回 | 现场测评 | PM 整套重做 |
| 报告分配 | 复核 | 原节点不动 | PM 收到整改通知 |
| 报告编制 | 驳回 | 现场测评 | PM 整套重做 |
| 报告编制 | 复核 | 原节点不动 | PM 收到整改通知 |
| **最终审核** | 复核 | **回报告编制**（原编制人）| 只改报告，不重新审核测评 |
| **最终审核** | 驳回 | **回现场测评** | PM 整套重做整个闭环 |

### ⚠️ 系统预留但未启用：调整动作

| 触发节点 | 触发动作 | 设计意图（如果启用）| 状态 |
|---|---|---|---|
| 最终审核 | 调整 | → 回现场测评 → PM 改测评数据 → **跳过 4 路质量审核** → 直达报告分配 | 后端代码已实现，前端无入口 |
| 报告编制（业务建议）| 调整 | 编制员发现测评数据小问题 → PM 微调 → 跳过 4 路质量审核 → 回报告编制继续编 | 未配置 |

## ⚠️ 关于"调整"动作（重点待业务确认）

### 现状

- 系统后端**预留**了第四种审核动作叫"调整"（ADJUST），与"通过/复核/驳回"并列
- 但前端审核弹窗只有 **3 个按钮**（通过/复核/驳回），**审核人无法选择"调整"**
- 因此当前业务流程**不会触发调整路径**

### 设计意图（推断）

调整 = "小改测评数据，但不重新走整套质量审核"。

**完整路径**（如果落地）：
```
最终审核员（或编制员）点"调整"
   ↓
回到现场测评（PM 微调测评数据）
   ↓ PM 改完点"发起质量审核"
直接进入"报告分配"（跳过整体技术审核 + 3 路内容审核！）
   ↓
报告编制 → 最终审核
```

**与其他动作的区别**：

| 动作 | 回到哪 | 是否重新做质量审核 | 适合场景 |
|---|---|---|---|
| 通过 | 下一节点 | — | 没问题 |
| 复核 | 原节点 / 报告编制 | 不需要 | 小问题，原岗位整改 |
| 驳回 | 现场测评 | **是**（4 路全部重做）| 测评本身有大问题 |
| **调整** | 现场测评 | **否**（跳过 4 路）| **测评数据有小问题，不值得整套重审** |

### 需要业务方拍板的问题

1. **业务上是否有这种"调整"场景？**
   - 比如：最终审核员看出某测评字段不对，但只需要 PM 改一下数字，不至于让 3 位内容审核员重新审一遍。
   - 如果业务上确实有这种需求 → 需要落地"调整"动作
   - 如果业务上"小改也走完整流程"是 OK 的 → 删掉这块死代码

2. **如果需要落地"调整"，加在哪些节点？**
   - **选项 A（当前设计）**：只在最终审核加 — 部门经理把关时触发
   - **选项 B（业务可能更高频）**：放在报告编制 — 编制员逐字使用测评数据时最容易发现问题
   - **选项 C（兜底设计）**：报告编制 + 最终审核 都能调整
   - **选项 D**：业务上不需要，删除死代码

## 关键业务规则

### 规则 1：回避机制
所有审核环节，**当前项目的 PM 和测评师不能审核自己项目**。

例外：如果某种角色的人全部都在当前项目里（理论上极少），系统会兜底放行（违反回避规则但避免流程卡死，日志会留 warning）。

### 规则 2：抢单 vs 定向
- **抢单**：整体技术审核、报告分配、最终审核（多人能看到同一条任务，先点先得）
- **定向**：内容审核（3 个特定的人）、报告编制（特定的报告编制员）

### 规则 3：必传文件
- 现场测评 → 发起质量审核前：测评成果文件**必须 ≥ 1 个**
- 报告编制 → 通过前：编制报告文件**必须 ≥ 1 个**

### 规则 4：复核 vs 驳回的语义
- **复核** = 小问题，不重启流程，原审核员等 PM 改完继续审
- **驳回** = 大问题，回到现场测评从头来，所有质量审核重做

业务上请明确：哪种程度的问题应该走复核，哪种应该走驳回。建议在审核员培训时讲清楚。

## 需要业务方确认的几个问题

### 问题 1：内容审核"复核"会让全员重审

**现状**：内容审核 3 路并行，任何一路"复核"会让已通过的另外两路也回到"待整改"，PM 改完后 3 个人都要重新审一遍自己已经审过的内容。

**业务方需要回答**：
- 是要保持"全员重审"（更保险）？
- 还是改成"只让点复核的那个人重审"（更省事，但 PM 修改可能影响其他人审核结论）？

### 问题 2：池任务的并发抢单

**现状**：整体技术审核、报告分配、最终审核都是池化任务，多个审核员能同时看到，先点先得。**没抢到的人在自己待办列表里还会看到这条任务**，等他再点会提示"该任务已被他人处理"。

**业务方需要回答**：
- 是接受这种"提示已被抢"的体验？
- 还是需要后端在有人抢到后实时推送，把其他人待办列表里这条任务隐藏？

### 问题 3：驳回距离差异

**现状**：质量审核任何一个节点驳回，**都直接回到现场测评**（最远回滚）。即使是报告编制阶段驳回也是回测评，不是只回到上一步。

**业务方需要回答**：
- 这种"驳回一律回测评"是符合业务预期的？
- 还是希望按驳回节点不同回到不同的上一步？比如报告编制驳回应该回内容审核，而不是回测评？

|---|---|
| 项目经理 PM | 上传测评成果，发起质量审核，整改 |
| 测评师 | 上传自己负责的测评资料 |
| 整体技术审核员（tech_reviewer）| 整体技术审核 |
| 内容审核员-技术（content_reviewer_tech）| 内容审核第 1 路 |
| 内容审核员-管理（content_reviewer_mgmt）| 内容审核第 2 路 |
| 内容审核员-网络（content_reviewer_network）| 内容审核第 3 路 |
| 报告分配人（report_assigner）| 选定报告编制人 |
| 报告编制员（report_writer）| 编写报告 |
