# 质量审核流程改造方案

> 配套文档：`docs/质量审核讨论.md`（改造目标的认知文档）
> 本文档：实施方案 + 清理清单 + 阶段拆分

---

## 0. 总览

### 0.1 改造目标
按照 `质量审核讨论.md` 的 8 节认知，对质量审核流程做一次彻底改造，包含：
- 工作流定义重构（删旧路径 + 加新机制）
- 死代码清理（ADJUST / rejectToTechReview / skip_to_final 等）
- 新数据模型（沟通事件 + 审核人持久化 + 文件池分类）
- 双视角 UI（流程时间轴 + 补充材料池）
- 注释 / 命名同步更新

### 0.2 改造原则
1. **每阶段独立可部署、可回滚** — 不出现"中间态不可用"
2. **新机制先上线、旧组件保留过渡** — 验证 OK 后再删旧
3. **死代码与新代码不并存** — 同阶段引入新功能就删对应死代码，避免认知混乱
4. **注释与代码同步** — 改完逻辑必查注释，发现 stale 注释立即更新或删除
5. **命名定义明确** — 字段 / 函数 / 状态值的命名要从代码注释 → schema → API 文档保持一致
6. **改动前查看测试 / 历史 commit** — 防止重蹈历史 bug

### 0.3 阶段总览

| 阶段 | 主题 | 风险 | 改动 | 工时 |
|---|---|---|---|---|
| **阶段 1** | Bug 修复 + 死代码清理 | 低 | 5 个点 | 1d |
| **阶段 2** | 数据库 schema 准备 | 低 | 新表 + 字段扩展 | 1d |
| **阶段 3** | 工作流定义改造 | 中 | transition + handler | 2d |
| **阶段 4** | 审核人持久化机制 | 中 | 新 binding 逻辑 | 1.5d |
| **阶段 5** | 沟通机制（核心新增）| 中 | 接口 + 通知 + UI | 4-5d |
| **阶段 6** | 报告编制重设计 | 中 | 双文件池 + 永久持有 | 3-4d |
| **阶段 7** | 双视角 UI | 低 | 新组件 + 并存 | 2d |
| **阶段 8** | 验证后清理 | 低 | 删旧组件 | 0.5d |
| **合计** | | | | **15-17d** |

## 1. 数据模型设计（DB 改动）

### 1.1 新增表 `project_reviewer_binding`（审核人持久化）

```sql
CREATE TABLE project_reviewer_binding (
    id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    project_id BIGINT NOT NULL,              -- 项目 id（project_register.id）
    node_key VARCHAR(64) NOT NULL,           -- 'TECH_REVIEW' / 'CONTENT_REVIEW' / 'FINAL_REVIEW'
    slot_key VARCHAR(64) NOT NULL DEFAULT '',-- CONTENT_REVIEW 用 'CONTENT_A/B/C'，其他为空
    user_id BIGINT NOT NULL,                 -- 绑定的审核人
    bound_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (project_id, node_key, slot_key)
);
```

**写入时机**：节点首次进入时，由 `review.handler.onEnter` 写入。
**读取时机**：节点重新进入时，先查 binding：
- 命中 + user enabled → 沿用，task.assignee_id = binding.user_id
- 命中 + user disabled → 按角色排序顺延，更新 binding
- 未命中 → 按 assignment_rule 取候选，写入 binding

### 1.2 新增表 `communication_event`（沟通事件）

```sql
CREATE TABLE communication_event (
    id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    project_id BIGINT NOT NULL,              -- 项目 id
    source_node_key VARCHAR(64) NOT NULL,    -- 触发时所在工作流节点
    event_type VARCHAR(32) NOT NULL,         -- 'WRITER_REQUEST' / 'PM_SUPPLY'
    initiator_id BIGINT NOT NULL,            -- 发起人 user_id
    message VARCHAR(1000) NOT NULL,          -- 备注（必填）
    attachment_file_id BIGINT,               -- 附件文件 id（关联到 report_file）
                                             --   WRITER_REQUEST: 可选（示例文件）
                                             --   PM_SUPPLY:      必填（补的材料）
    related_event_id BIGINT,                 -- PM_SUPPLY 响应某个 WRITER_REQUEST 时关联
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_communication_event_project ON communication_event(project_id, created_at);
```

**event_type 枚举说明**：
- `WRITER_REQUEST` — 编制人请 PM 补材料（"沟通"按钮触发）
- `PM_SUPPLY` — PM 主动补 / 响应编制人请求（同一事件，区别在 `related_event_id` 是否非空）

### 1.3 改造现有表 `compile_report_file` → `report_file`

**改名 + 加字段**（也可以保留旧表名，但语义已扩展，**强烈建议改名**避免认知混乱）：

```sql
-- migration:
ALTER TABLE compile_report_file RENAME TO report_file;
ALTER TABLE report_file ADD COLUMN pool_type VARCHAR(32) NOT NULL DEFAULT 'FINAL_REPORT';
ALTER TABLE report_file ADD COLUMN source_node_key VARCHAR(64);
ALTER TABLE report_file RENAME COLUMN compiled_by TO uploaded_by;

-- pool_type 枚举：
-- 'FINAL_REPORT'      最终报告（编制人上传，永远只读）
-- 'REPORT_MATERIAL'   报告材料（编制人上传，永久可改）
-- 'SUPPLEMENT'        补充材料（沟通附件，上传后只读）
```

**为什么不沿用 `assessment_file.file_pool`**：
- assessment_file 是测评阶段的文件池（ASSESSMENT_FILE / ASSESSMENT_RESULT），语义不同
- 报告相关文件与测评文件应分表存储，避免单表混杂

### 1.4 schema 改动汇总

| 表 | 操作 | 字段 |
|---|---|---|
| `project_reviewer_binding` | 新建 | id, project_id, node_key, slot_key, user_id, bound_at, updated_at |
| `communication_event` | 新建 | id, project_id, source_node_key, event_type, initiator_id, message, attachment_file_id, related_event_id, created_at |
| `compile_report_file` | 重命名为 `report_file` + 加字段 | + pool_type, + source_node_key, compiled_by → uploaded_by |

**改后**：
```ts
} else if (action === 'REVIEW') {
  if (!remark || ...) throw ...;

  // 第 1 步：只更新触发复核的任务，挂上他自己的 remark
  await ctx.db.update(wfTask).set({
    status: 'PENDING_RECTIFICATION',
    result: 'REVIEW',
    remark,
    updatedAt: new Date(),
  }).where(eq(wfTask.id, taskId));

  // 第 2 步：其他任务进入待整改状态，但保留各自的 remark 和 result（如果有）
  await ctx.db.update(wfTask).set({
    status: 'PENDING_RECTIFICATION',
    updatedAt: new Date(),
  }).where(and(
    eq(wfTask.instanceId, ctx.instance.id),
    eq(wfTask.nodeKey, ctx.nodeDef.nodeKey),
    inArray(wfTask.status, ['PENDING', 'COMPLETED']),
    ne(wfTask.id, taskId),
  ));

  return false;
}
```

**更新注释**：
```ts
// 任意一个审核人触发 REVIEW → 整个节点的任务都进入待整改：
// - 触发者的任务挂上他的 remark（A 写了什么 PM 整改时能看到）
// - 其他审核人的 remark 保留原值（避免覆盖 B 已通过时填的"通过"备注）
// PM 整改后 resubmitFromRectification 把所有任务清空 remark 重新审。
```

新增方法 `resolveAssigneeWithBinding`：

```ts
async resolveAssigneeWithBinding(
  nodeKey: string,
  slotKey: string | null,
  projectId: number,
  alreadyAssigned: number[],
  roleCodeOverride?: string,
): Promise<number | null> {
  // 1. 查 binding
  const binding = await this.db.select()
    .from(projectReviewerBinding)
    .where(and(
      eq(projectReviewerBinding.projectId, projectId),
      eq(projectReviewerBinding.nodeKey, nodeKey),
      eq(projectReviewerBinding.slotKey, slotKey ?? ''),
    ))
    .limit(1);

  if (binding[0]) {
    // 2a. 命中：检查 user 是否 enabled
    const user = await this.db.select({ enabled: userAccount.enabled })
      .from(userAccount)
      .where(eq(userAccount.id, binding[0].userId))
      .limit(1);
    if (user[0]?.enabled) {
      return binding[0].userId;  // 沿用
    }
    // 2b. 命中但被禁用：按角色排序顺延
    const newId = await this.resolveAssignee(nodeKey, slotKey, projectId, [binding[0].userId], roleCodeOverride);
    if (newId) {
      await this.db.update(projectReviewerBinding)
        .set({ userId: newId, updatedAt: new Date() })
        .where(eq(projectReviewerBinding.id, binding[0].id));
    }
    return newId;
  }

  // 3. 未命中：走原 resolveAssignee + 写入 binding
  const newId = await this.resolveAssignee(nodeKey, slotKey, projectId, alreadyAssigned, roleCodeOverride);
  if (newId) {
    await this.db.insert(projectReviewerBinding).values({
      projectId, nodeKey, slotKey: slotKey ?? '', userId: newId,
    });
  }
  return newId;
}
```

## 6. 风险点 + 注意事项

### 6.1 数据迁移风险

| 风险 | 描述 | 缓解 |
|---|---|---|
| `compile_report_file` → `report_file` 改名 | drizzle 可能生成 DROP+CREATE 导致数据丢失 | 手工编辑 migration 改为 ALTER TABLE RENAME + ALTER COLUMN |

```
阶段 8 编码 + 验证  →  阶段 8 上线（删除旧组件）
```

**重要**：每阶段上线前都要看一次 `git diff origin/master..HEAD --stat` 确认改动范围与方案一致。
