# 质量审核流程（改动后完整认知）

> 本文档只描述改动后的目标状态，不包含讨论、质疑、改动成本等内容。
> 涉及代码 / 数据库术语用「中文（英文）」对照。

---

## 1. 流程总览图

```
现场测评（ON_SITE_ASSESSMENT）
   │ PM 上传测评成果 + 发起质量审核
   ▼
整体技术审核（TECH_REVIEW）
   │ 通过
   ▼
内容审核（CONTENT_REVIEW，3 路并行）
   │ 全部通过
   ▼
┌─ 报告分配（REPORT_ASSIGN）              ← 首次走到这里
│     │ 通过 + 选定编制人
│     ▼
└─ 报告编制（REPORT_COMPILE）              ← 后续若驳回回测评，重走时直接到这里
       │ 提交材料（必填最终报告）
       ▼
   最终审核（FINAL_REVIEW）
       │
       ├─ 通过 → 材料归档（MATERIAL_ARCHIVE，出闭环）
       ├─ 复核 → 报告编制（原编制人）
       └─ 驳回 → 现场测评（重走时跳过报告分配）
```

**贯穿全流程的"沟通 / 补充材料"机制**：PM 和报告编制人在任意节点均可主动发起，详见第 4 节。

---

## 2. 节点详情

### 2.1 现场测评（ON_SITE_ASSESSMENT）

| 项 | 说明 |
|---|---|
| 谁在做 | 项目经理 PM（project_manager）+ 测评师们（senior/middle/junior_assessor + 项目 ASSESSOR 成员）|
| 任务分配 | 进入节点时按 `project_member` 中 PM + 所有 ASSESSOR 逐人创建任务 |
| 操作 | 各自上传文件；PM 整理"测评成果" |
| 触发下一步 | PM 点"发起质量审核"按钮 |
| 必填项 | **测评成果池（ASSESSMENT_RESULT）至少有 1 个文件** |
| 完成后 | → 整体技术审核 |

---

### 2.2 整体技术审核（TECH_REVIEW）

| 项 | 说明 |
|---|---|
| 谁在做 | 整体技术审核员（tech_reviewer） |
| 任务分配方式 | **按 tech_reviewer 角色排序取第一个**；若该用户是当前项目成员（PM / 测评师），**顺延下一个**；若全部 tech_reviewer 都在项目里，**兜底取第一个**（无视回避，留日志 warning）|
| 审核人持久化 | **首次确定后，该项目的整体技术审核人不再变更**。最终审核驳回回测评、再次走到此节点时，依然是同一人；若原审核人**被禁用**则顺延下一个；若没有候选则 super_admin 兜底 |
| 操作选项 | **通过** / **复核** |
| 通过后 | → 内容审核 |
| 复核后 | 当前节点不动，PM 收到整改通知，PM 改完点重新提交后**原审核员继续审** |
| 无驳回路径 | 本节点没有驳回功能 |

---

### 2.3 内容审核（CONTENT_REVIEW，3 路并行）

| 项 | 说明 |
|---|---|
| 谁在做 | 3 个人**同时**审：内容审核员-技术（content_reviewer_tech）/ 内容审核员-管理（content_reviewer_mgmt）/ 内容审核员-网络（content_reviewer_network）|
| 任务分配方式 | 3 个 slot 各自按对应角色排序取第一个；项目成员（PM / 测评师）顺延；若该角色全部都在项目里，兜底取第一个（无视回避，留日志 warning）|
| 审核人持久化 | **首次确定后，3 路审核人不再变更**。最终审核驳回回测评、再次进入此节点时，3 个 slot 依然是同一组人；若某 slot 的原审核人**被禁用**，按该角色排序顺延下一个；若无候选则 super_admin 兜底 |
| 操作选项 | 每人独立操作：**通过** / **复核** |
| 全部通过 | → 报告分配（首次） / 报告编制（已分配过） |
| 任一人复核 | 触发整改 → 3 个人的任务都进"待整改"状态，PM 收到通知；PM 改完后**3 人重新审**自己的部分。**每个人的复核 remark 独立保留**（不再共享）|
| 无驳回路径 | 本节点没有驳回功能 |

---

### 2.4 报告分配（REPORT_ASSIGN）⭐ 一次性节点

| 项 | 说明 |
|---|---|
| 谁在做 | 报告分配人（report_assigner） |
| 任务分配方式 | 按 report_assigner 角色排序取第一个，**不遵循回避** |
| 操作 | 选定一位报告编制人（report_writer）+ 点通过 |
| 通过后 | 编制人写入 `project_member.REPORT_WRITER`，下一步报告编制任务定向分配给他 → 进入报告编制 |
| **流程驳回后的行为** | **本节点终身不再走**。即使最终审核驳回 → 流程回测评 → 重走 4 路质量审核后，**直接跳到报告编制**（不重新分配）|
| 无复核 / 无驳回 | 本节点只有"通过"一个动作 |

**报告分配人的兜底权限**：
- 报告分配人能看到**全部报告列表数据**（不限于自己分配过的）
- **仅在原编制人被禁用（user_account.enabled = false）时**，报告分配人有权限重新指派编制人
- 重新指派 = 改 `project_member.REPORT_WRITER` + 改 REPORT_COMPILE 任务的 assigneeId

---

### 2.5 报告编制（REPORT_COMPILE）

| 项 | 说明 |
|---|---|
| 谁在做 | 报告分配阶段选定的报告编制员（report_writer） |
| 任务分配方式 | 定向分配（其他编制员看不到）|
| 操作选项 | **沟通** / **提交材料** |
| 上传分两个区 | • **最终报告**（FINAL_REPORT 池，必填）<br>• **报告材料**（REPORT_MATERIAL 池，选填）|
| 沟通 | 不阻断流程；详见第 4 节 |
| 提交材料 | **前置校验：最终报告池 ≥ 1 个文件**，否则不能提交 → 进入最终审核 |
| 无复核 / 无驳回 | 编制人没有否决权，只能推进流程 |

**编制人的特殊可见性**：
- 处理过这个项目的编制人，**该项目永远在他的"我的报告列表"里**（即使流程已完结甚至归档）
- 流程进行中：能编辑两个文件池
- 流程结束后 / 归档后：
  - **最终报告**永远只读（前端无编辑入口，后端不强制约束 — 后续可加"申请修改最终报告"流程）
  - **报告材料**：随时可编辑、新增、删除（因为存在"先最终审核盖章前的版本，盖章后还要更新"的场景）

---

### 2.6 最终审核（FINAL_REVIEW）

| 项 | 说明 |
|---|---|
| 谁在做 | 部门经理（dept_manager） |
| 任务分配方式 | 按 dept_manager 角色排序取第一个，**不遵循回避** |
| 审核人持久化 | **首次确定后，该项目的最终审核人不再变更**。无论复核回报告编制后再回来，还是驳回回测评、重走整套流程后再次进入，都是同一人；若被禁用则顺延下一个；若无候选则 super_admin 兜底 |
| 操作选项 | **通过** / **复核** / **驳回** |
| 通过后 | → 材料归档（出质量审核闭环）|
| 复核后 | → **回报告编制**，原编制人继续改报告（可走沟通也可直接改后提交）|
| 驳回后 | → **回现场测评**，PM 重做测评 + 重新走 4 路质量审核，但**跳过报告分配**直接到报告编制（沿用首次分配的编制人）|

---

## 3. 驳回 / 复核路径汇总表

| 触发节点 | 触发动作 | 实际回到哪 | 影响范围 |
|---|---|---|---|
| 整体技术审核 | 复核 | 原节点不动 | PM 整改测评成果，原审核员重审 |
| 内容审核（任一路）| 复核 | 原节点不动 | PM 整改，**3 人重新审自己部分（remark 独立）** |
| 报告编制 | 沟通 | 原节点不动，非阻断 | PM 收到补材料请求（详见第 4 节）|
| 最终审核 | 复核 | 报告编制（原编制人）| 编制人改报告，可走沟通或直接改后提交 |
| 最终审核 | 驳回 | 现场测评 | PM 整套重做（**重走时报告分配跳过**，沿用原编制人）|

**质量审核 4 路（技术 + 3 路内容）只有通过 / 复核，无驳回**。能让流程回到测评的只有最终审核的驳回。

## 4. 沟通 / 补充材料机制（贯穿全流程）

### 4.1 发起方与场景

> **起始时机**：沟通 / 补充材料机制**仅在质量审核流程启动后生效**（即 PM 点了"发起质量审核"按钮，流程进入整体技术审核之后）。
> 现场测评阶段 PM 和测评师团队的协作不走"沟通"，直接通过上传测评材料 / 测评成果完成；该阶段不发提醒。

| 发起方 | 场景 |
|---|---|
| **报告编制人**（report_writer）| 编制阶段发现 PM 给的材料缺失 / 数据有问题，主动请 PM 补充 |
| **项目经理 PM**（project_manager）| 在质量审核启动后的**任意节点**自己发现漏材料，主动上传补充 |

### 4.2 数据字段

每条补充材料记录包含：
- 文件（必填，支持任意类型附件）
- 备注（必填）
- 自动记录：上传人 / 时间 / 触发节点
- 关联项目（project_register_id）

### 4.3 可见性

**所有有该项目可见性的人**都能看到补充材料（流程透明）：
- 当前节点的审核人（实时可见）
- 已审过的人（历史可见）
- 后续节点的审核人（流程流转后能拿到最新数据）
- PM、销售、项目主管、超级管理员、董事长（按各自的项目可见性规则）

### 4.4 提醒机制

**只提醒当前节点的相关方**，不提醒后续节点的审核人（防止提醒泛滥，否则最终审核员会从质量审核启动开始就被一直提醒）。

| 触发场景 | 提醒接收人 |
|---|---|
| 编制人发起沟通（请 PM 补材料）| **PM**（当前节点的"补材料方"）|
| PM 补充材料后（响应编制人请求）| **编制人** |
| PM 在整体技术审核阶段主动补 | **当前的整体技术审核员**（不提醒后续内容审核员、编制人、最终审核员）|
| PM 在内容审核阶段主动补 | **当前 3 个内容审核员**（不提醒后续）|
| PM 在报告编制阶段主动补 | **当前编制人**（不提醒最终审核员）|
| PM 在最终审核阶段主动补 | **最终审核员** |

**不在沟通机制范围内的场景**：
- 现场测评阶段（PM 和测评师团队的协作不属于"沟通"，直接上传材料即可）
- 报告分配阶段（分配人只做单次分配动作，无沟通对象）

**核心原则**：后续节点的审核人在自己节点开始时**自动看到截至当时的全部补充材料**（从文件池 / 时间轴拉最新数据），不需要在前面阶段就被提醒。

通知触达：系统铃铛 + （配置开启时）钉钉推送

### 4.5 展示方式（双视角）

**视角 A — 流程时间轴（在项目详情 / 任务详情页）**：
审核历史时间线里**插入沟通条目**，与审核动作混排：

```
─ 2026-05-12 09:00  PM 张三  提交项目
─ 2026-05-13 14:00  审核员 李四  整体技术审核通过
─ 2026-05-14 11:00  审核员 赵六  内容审核（技术）复核 — "证据 X 缺失"
─ 2026-05-14 15:00  PM 张三  📎 补充材料 — "已补证据 X" [附件:证据X.pdf]
─ 2026-05-14 16:00  审核员 赵六  内容审核（技术）通过
─ 2026-05-15 09:00  分配人 钱七  报告分配 — 编制人：孙八
─ 2026-05-15 14:00  编制人 孙八  📎 沟通 — "测评结论表第 3 行缺单位盖章件" [附件:盖章件模板.pdf]
─ 2026-05-16 11:00  PM 张三  📎 补充材料 — "已补盖章件" [附件:盖章件.pdf]
─ 2026-05-16 15:00  编制人 孙八  提交最终报告
```

**视角 B — 独立的"补充材料"池**：
在文件管理里增加 `SUPPLEMENT_MATERIAL` 池（与测评成果 / 最终报告 / 报告材料并列）。

按节点、上传人、时间筛选：

```
[补充材料池]
├─ 证据X.pdf       · PM 张三 上传       · 内容审核阶段       · 备注："已补证据 X"        · 2026-05-14 15:00
├─ 盖章件.pdf      · PM 张三 上传       · 报告编制阶段       · 备注："已补盖章件"        · 2026-05-16 11:00
└─ ...
```

- 编制人写报告时可直接在这个池单独筛选 PM 补的材料，方便引用

### 4.5.1 与旧审核历史组件的关系（过渡期）

**当前已有的审核历史展示组件**（`ReviewOpinionHistory`、`ReviewOpinionPanel`）**先不删除**，与新组件**并存展示**：

| 展示位置 | 旧组件 | 新组件 |
|---|---|---|
| 项目详情页 / 任务详情页 | 保留：原"审核意见历史"面板 | 新增：流程时间轴（含审核 + 沟通） |
| 任务详情页 | 保留：审核动作的弹窗操作面板 | — |
| 文件管理区 | — | 新增：补充材料池视图 |

**过渡策略**：
1. 新组件上线后，两者同时展示一段时间
2. 用户验证新视角能完整覆盖旧组件的信息（同时更直观）
3. 确认后再删除旧组件

### 4.6 沟通限制

- 不限制轮次
- 暂不实现"已读 / 已回复"状态
- 年度统计指标后期再确定（数据上 100% 留痕，方便日后统计）

## 7. 关键业务规则汇总

| 规则 | 说明 |
|---|---|
| **回避机制** | 整体技术审核 / 内容审核遵循回避：当前项目的 PM 和测评师不能审核自己项目。如果某种角色的人全在当前项目里，兜底按序选择第一个，无视回避（日志留 warning）。**报告分配 / 最终审核不遵循回避** |
| **审核人持久化** | 整体技术审核、内容审核 3 路、最终审核：**首次确定的审核人写入持久化**（建议新表 `project_reviewer_binding` 或复用 `project_member`）；后续重新进入该节点时**沿用同一人**，被禁用则按角色排序顺延，全无候选则 super_admin 兜底 |
| **任务分配机制** | 质量审核 4 路全部按角色 `user_role.sort_order` 取第一个候选人，**不是抢单**：<br>• 整体技术审核 / 内容审核 3 路：遵循回避规则（项目成员顺延）+ 审核人持久化（首次确定后不再变更）<br>• 报告分配 / 最终审核：不遵循回避；最终审核同样有持久化<br>• 报告编制：由报告分配人选定 |
| **必传文件** | 现场测评 → 发起质量审核前：测评成果 ≥ 1 个；报告编制 → 提交前：最终报告 ≥ 1 个 |
| **复核语义统一** | 所有节点的"复核"都是"原审核人留在原地，等修正方提交后继续审"，不重启流程 |
| **驳回入口仅在最终审核** | 质量审核 4 路只有通过 / 复核，能让流程回测评的只有最终审核的驳回 |
| **报告分配一次性** | 一旦分配过编制人，该项目终身不再走报告分配节点。例外：原编制人被禁用，由报告分配人重新指派 |
| **最终报告不可改** | 提交后前端无编辑入口（后端不强制约束）。后续可加"申请修改最终报告"流程 |
| **报告材料永久可改** | 编制人对自己处理过的项目报告材料**永远**有编辑权（包括归档后）|
| **沟通透明** | 所有项目相关方都能看到补充材料 + 时间轴中的沟通条目 |
| **内容审核 remark 独立** | 3 路并行中每个审核人的复核意见独立存储，不再被覆盖 |
